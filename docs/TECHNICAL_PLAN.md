# Technical plan

## Status
The official `fullstack-web` scaffold and a first app shell are present. Package versions are pinned by the generated manifest and QoreX provider types. Contract API, addresses, and deployment commands are still unconfirmed because no contract has been deployed.

## Proposed architecture
- Web client generated by `create-qorechain-dapp@0.14.0 --template fullstack-web`.
- QoreX native provider via `@qorechain/qorex-types`; the wallet retains keys and approves hybrid native-lane transactions.
- If the provider is absent, show a locally generated QR for the current app URL and instructions to open that URL in QoreX's mobile dApp browser. The browser injects the native provider on that origin. This is an app URL handoff, not a remote wallet pairing session; a public HTTPS deployment is required for another device to reach it.
- Minimal on-chain event registry or supported module for event metadata and check-in status.
- Read path through official SDK/API/REST and explorer; receipts are checked against fresh chain data.

### Candidate on-chain behavior
- Create event with unique ID and minimal metadata.
- Organizer opens/closes check-in.
- Attendee checks in once; contract/module emits a receipt event.
- Read event and whether an address checked in.

Keep personal data off-chain and disclose that event/transaction data is public. Consider storing a title commitment/hash instead of plaintext title if usability permits.

## Hybrid-signature integration gate
Quantum Pass explicitly requires a hybrid-signed transaction. EVM contract calls and native-lane hybrid transactions have different signing paths. Do not assume an ordinary EVM transaction itself carries an ML-DSA signature.

Before calling the flow complete:
1. Connect QoreX through its native provider and submit a real testnet message.
2. Require `shield: shielded` and verify the chain's PQC verification result where the query API exposes it.
3. Read the resulting transaction back from the testnet and validate chain ID, transaction hash, event/check-in relation, and receipt data.
4. Record the actual hash and evidence link. Do not count an EVM transaction alone as the hybrid-signature demonstration.

The current QoreX integration docs expose native `signAndBroadcast`, which returns `txHash`, `code`, `height`, and a `shield` status. The app must require `shielded` before calling a transaction hybrid verified. The EVM connector in the kit is read-only in current QoreX builds. A user may see key registration followed by the requested transaction; explain each wallet prompt and show separate submission/confirmation states.

QoreX's `qorex://connect` pairing and proof APIs are reserved to the QoreChain Dashboard origin. Do not reuse that flow or imply a QR scan remotely connects a phone wallet to the desktop browser. QoreX's supported general dApp flow is to open the app inside its in-app dApp browser and approve the site's connection there. References: [QoreX dApp Browser](https://docs.qorechain.io/qorex/dapp-browser/), [QoreX Integrations](https://docs.qorechain.io/developer-tools/qorex-integrations/).

## Candidate data model
- Event: `eventId`, `organizer`, `title` or `titleHash`, `checkInOpen`.
- Check-in: `eventId`, `attendee`, transaction/log reference, block number.
- Uniqueness: `(eventId, attendee)`.

Adapt this to the chosen runtime and scaffold; do not treat it as a final ABI.

## Security and privacy
- Testnet only; no real funds or production credentials.
- Never handle private keys or seed phrases.
- Treat address as pseudonymous identifier, not human identity.
- Minimize on-chain data; chain data is public and durable.
- Verify chain ID and contract address on every write/read.
- Fail closed on missing or inconsistent chain data.
- Enforce permissions in the contract/module, not only frontend.

## Open decisions

3. Which QoreX connector is supported by the generated template?
4. Which official API/explorer fields reliably prove a transaction and signature verdict?
5. Is public event title acceptable, or should chain store a commitment?
